Run the DORSI Nokia lab from scratch

A step-by-step guide for someone who has never started the lab. You will deploy a small data center fabric of Nokia SR Linux switches and servers, let DORSI configure every switch, and check the result in the terminal and in the Web UI. The same steps run the mixed labs of Nokia and Arista switches, including a 5-stage fabric.

What you will build

The lab is a 3-stage Clos fabric: three leaf switches, each connected to both of the two spine switches. Servers hang off the leaves, and two of them are connected to two leaves (dual-homed). You describe this network in one short file, ip-fabric.xml. DORSI turns the description into the configuration of each switch: loopbacks, point-to-point addresses, eBGP sessions and ECMP.

Before you start

You needNotes
Docker, with at least 9 GB of RAM available to itWith less, SR Linux nodes lose their dataplane (xdp_lc_1 has failed) and cannot be configured. 12 GB is comfortable.
A Linux host, or macOS with ColimaThe Makefile is written for Colima on macOS. Docker Desktop has not been verified for this lab.
git, make, curlStandard tools.
Internet access to ghcr.io and GitHubThe first run downloads the SR Linux and server images and, if you choose it, a prebuilt dorsi binary.
Acton (optional)Only if you build dorsi from source instead of downloading it.

You do not need a Nokia account or license: the ghcr.io/nokia/srlinux image is public. You do not need to install Containerlab either, because the Makefile runs it from a container.

macOS: start Colima with enough memory

Terminal
$ brew install colima docker
$ colima start --cpu 4 --memory 12
$ docker info | grep -i 'total memory'
 Total Memory: 11.67GiB

example output Anything of 9 GiB or more is fine.

Step by step

Each command block has a Copy button. Run everything from a terminal. Output blocks marked example output show what you should roughly see; exact timings, addresses of the management network and uptime values will differ.

1

Get the code

Terminal
$ git clone https://github.com/stratoweave/dorsi.git
$ cd dorsi
$ git checkout main

All later commands are run from this dorsi directory unless a step says otherwise.

2

Get the dorsi binary for Linux

The binary runs inside the sweave container, so it must be built for Linux, even on a Mac. Pick one option. Both leave the file at out/bin/dorsi.

Option A: download the prebuilt release (fastest). This is the tip release from GitHub and may differ from your local checkout.

dorsi/
$ make download-release
Note: Downloading Linux binary for use in container (e.g., Colima)
Downloading dorsi-linux-aarch64.tar.gz from GitHub...
Extracting binary...
Download complete: out/bin/dorsi

Option B: build from source (needs Acton). Use the target that matches your CPU (uname -m).

dorsi/
# Apple Silicon / ARM
$ make build-linux-aarch64
# Intel / AMD
$ make build-linux-x86_64
3

Start the lab

Pick a free port on your machine for the Web UI (3100 below; the default is 3000). The first run pulls images and can take several minutes.

dorsi/test/fabric-3stage
$ cd test/fabric-3stage
$ WEBUI_PORT=3100 make start
... building dorsi-sweave-base, pulling ghcr.io/nokia/srlinux:25.3.2 ...
... containerlab deploy ...
DORSI Web UI: http://localhost:3100

When it returns, check that all nine containers exist:

Terminal
$ docker ps --format '{{.Names}}\t{{.Status}}' | grep dorsi-fabric-3stage
dorsi-fabric-3stage-leaf1     Up 2 minutes
dorsi-fabric-3stage-leaf2     Up 2 minutes
dorsi-fabric-3stage-leaf3     Up 2 minutes
dorsi-fabric-3stage-spine1    Up 2 minutes
dorsi-fabric-3stage-spine2    Up 2 minutes
dorsi-fabric-3stage-server1   Up 2 minutes
dorsi-fabric-3stage-server2   Up 2 minutes
dorsi-fabric-3stage-server3   Up 2 minutes
dorsi-fabric-3stage-sweave    Up 2 minutes

example output Nine rows: 5 switches, 3 servers, 1 sweave.

Wait before the next step. SR Linux needs a minute or more to boot. Configuring a switch that has not finished booting is the most common reason for errors. Check one switch with the command below; when it answers, the switch is ready.
dorsi/test/fabric-3stage
$ docker run --rm --network container:dorsi-fabric-3stage-sweave ghcr.io/stratoweave/ncurl \
    --host leaf1 --port 830 --username clab --password clab@123 hello
A NETCONF hello reply means ready. A connection error means: wait 30 seconds and try again.
4

Let DORSI configure the switches

This copies the binary and the fabric description (ip-fabric.xml) into the sweave container and starts DORSI there.

dorsi/test/fabric-3stage
$ make copy
$ make run-and-configure
... DORSI logs ...
StratoWeave running

run-and-configure keeps running in the foreground and prints DORSI's log. Leave this terminal open and open a second one for the next step. Stop DORSI later with Ctrl+C.

Prefer to run it in the background? Use docker exec -d dorsi-fabric-3stage-sweave sh -c '/dorsi ip-fabric.xml > /dorsi.log 2>&1' and read the log from /dorsi.log inside the container.
Shortcut for steps 2 to 4: make dev-tutorial downloads the release, starts the lab, waits 30 seconds, copies the files and runs DORSI. Use it only if the 30-second wait is enough on your machine.
5

Check the fabric on a switch

Open the SR Linux CLI on leaf1:

second terminal
$ docker exec -it dorsi-fabric-3stage-leaf1 sr_cli
A:leaf1#

BGP sessions. Leaf1 should have two eBGP neighbors, one per spine, both established:

leaf1 (sr_cli)
A:leaf1# show network-instance default protocols bgp neighbor
+--------------+------------+------------------+
| Peer         | Peer-AS    | State            |
+--------------+------------+------------------+
| 10.100.0.227 | 4200100101 | established      |
| 10.100.0.229 | 4200100101 | established      |
+--------------+------------+------------------+

example output Simplified columns. Peer addresses and AS numbers are the ones DORSI derives for this topology. What matters is the State column. Each spine has three sessions, one per leaf.

Routes. Leaf1 should know the loopback of every other switch, and reach the other leaves through both spines (ECMP):

leaf1 (sr_cli)
A:leaf1# show network-instance default route-table ipv4-unicast summary
Prefix           Next hops                      Protocol
10.0.0.2/32      10.100.0.227, 10.100.0.229     bgp      <- two paths (ECMP)
10.0.0.3/32      10.100.0.227, 10.100.0.229     bgp      <- two paths (ECMP)
10.0.0.11/32     10.100.0.227                   bgp
10.0.0.12/32     10.100.0.229                   bgp

example output Simplified and shortened for readability; the real command prints more columns and your own link and local routes as well.

Leave the CLI with Ctrl+D.

What has and has not been verified. On the 3-stage lab all eBGP sessions come up, and ECMP and loopback reachability work. Server-to-server traffic, link or leaf failures and live changes to a running fabric are not covered yet.
6

Open the Web UI

Go to http://localhost:3100 (your WEBUI_PORT). The UI is served by DORSI inside the lab and listens on 127.0.0.1 only. The REST API (RESTCONF) is under /restconf on the same port. It has no authentication, which is why it is not exposed to the network.

Continue with What the Web UI shows to see what each page should look like.

What the Web UI shows

About these screenshots. They are real screenshots of the DORSI Web UI, taken from the same ip-fabric.xml with the switches switched to mock mode (no containers). In the real lab the layout is identical. The differences: switches do not carry the MOCK badge, and the mock line is absent from the configuration views.

Dashboard: the fabric at a glance

What to look for

  • Devices 5, All configured and Pending approvals 0.
  • Fabric switches 5, Fabric links 6.
  • The topology map: spine1, spine2 on top, leaf1 to leaf3 below, three servers at the bottom, with port names on the links. It matches the diagram at the top of this guide.
  • The Live indicator at the top right is green.

Devices

What to look for

  • Five cards, one per SR Linux switch (NokiaSRLinux_25_3_2), all Configured. Servers are not listed because DORSI does not manage them.
  • A card that is not green means DORSI could not reach or configure that switch. See When something is wrong.

One device

What to look for

  • Running config and Target config both Present.
  • Queue length 0 and Pending approvals 0: nothing is waiting to be sent.
  • The buttons at the top right: Configuration (what is on the device), Log (what DORSI sent) and Resync (re-read the device).

Layer configuration: from your description to the device

What to look for

  • Three layers: 0 · CFS is what you wrote (the fabric), 1 · RFS is the intermediate result, 2 · Device is the final configuration per switch.
  • On layer 2, leaf1 has interface descriptions such as Link to spine2 [ethernet-1/1] and addresses such as 10.100.0.228/31.
  • You can switch the format between XML, JSON and AData, and copy the text.

Services: edit the fabric

What to look for

  • Five switches of fabric dc1 with role badges LEAF and SPINE.
  • You can edit, clone or remove entries of the existing fabric. A brand-new fabric needs at least two switches and one link in one go, so it is created through RESTCONF or a startup file, not through these forms.

Addressing cheat sheet

You only describe switches, links and servers. DORSI derives the rest from each switch's id.

WhatRuleExample in this lab
Loopback10.0.<id / 256>.<id % 256>leaf1 (id 1) is 10.0.0.1; spine2 (id 12) is 10.0.0.12
Link addressesone /31 from 10.100.0.0/16 per (lower switch, lower port)leaf1 e1/49 is 10.100.0.226/31, spine1 e1/1 is 10.100.0.227/31
AS numberone per leaf; one per spine pod and plane; one per super-spine planeleaves 4200000001 to 4200000003; both spines 4200100101; a super-spine of plane 1 is 4200200001

Limits: switch id up to 511 and a lower port number below 64.

When something is wrong

What you seeLikely cause and fix
xdp_lc_1 has failed in an SR Linux log, switch cannot be configuredNot enough memory. Give Docker or Colima at least 9 GB (12 GB is safer), then make stop and start again.
make start says the port is already in useChoose another one: WEBUI_PORT=3200 make start. Two labs at once need different ports.
make copy: no such file out/bin/dorsiStep 2 was skipped. The binary must be in out/bin/dorsi in the repository root, not in test/fabric-3stage.
exec format error when DORSI startsThe binary is for the wrong CPU or for macOS. Rebuild with the Linux target that matches uname -m.
make download-release fails to downloadNo prebuilt binary exists for your platform. Build from source (step 2, option B).
NETCONF connection errors in the DORSI logA switch is still booting (see the wait in step 3). Wait, then stop DORSI with Ctrl+C and run make run-and-configure again.
Image pull errors from ghcr.ioCheck internet access and proxy settings. The images are public. A stale login can get in the way: docker logout ghcr.io.
pull access denied for ceos when a mixed lab startsThe cEOS image is not in a public registry. Download and import it, see Get the cEOS image.
exec: "xz": executable file not found on docker importThe Docker daemon (in the Colima VM) has no xz. Decompress on the Mac instead: xz -dc <file> | docker import - ceos:4.36.3.2M.
DORSI loses an Arista switch right after configuring itThe switch has no management-address in ip-fabric.xml. EOS keeps its management address in the configuration DORSI manages, so without one DORSI removes it from Management0.
NETCONF authentication fails on an Arista switchThe lab startup file turns on password login for SSH (authentication protocol keyboard-interactive password public-key). It takes a few seconds after boot; wait until show management api netconf says running.
make get-dev-config-leaf1 or make save-logs do nothingThese shared make targets only know XR and cRPD routers, not SR Linux. Use sr_cli and docker logs as shown above.

See the UI without containers

If you only want to explore DORSI and its Web UI, you do not need SR Linux or 9 GB of RAM. In mock mode DORSI pretends the switches exist. The screenshots above were made this way.

Copy ip-fabric.xml and add <mock>true</mock> to every switch, then start DORSI with a port of your choice:

dorsi/test/fabric-3stage
$ sed 's#\(<role>.*</role>\)#\1<mock>true</mock>#' ip-fabric.xml > ip-fabric-mock.xml
$ ../../out/bin/dorsi --http.port 8089 ip-fabric-mock.xml
StratoWeave running

Open http://localhost:8089. The binary must run on your own system: on a Mac, build it with make build-macos-aarch64, which overwrites out/bin/dorsi, so rebuild the Linux binary before using the real lab again. On Linux the Linux binary works directly.

In mock mode the log may contain subscription errors such as Child 'session-state' not found. They come from the missing device and do not stop the UI.

Mixed Nokia and Arista labs

One fabric can mix Nokia SR Linux and Arista EOS switches. DORSI configures EOS through OpenConfig and gives it the same fabric as SR Linux: loopback, /31 links, eBGP with ECMP and LLDP. Two labs replace some of the Nokia switches with Arista cEOS-lab containers.

LabTopologySwitchesMemoryStatus
test/fabric-3stage-mixed3-stage: 3 leaves, 2 spines3 Nokia, 2 Arista (leaf3, spine2)~8 GBRun: all eBGP sessions up, ECMP and loopbacks work
test/fabric-5stage-mixed5-stage: 2 pods, 1 plane2 Nokia, 3 Arista (leaf1, spine2, superspine1)~8 GBRun: all eBGP sessions up, loopbacks reachable across all five stages

Each SR Linux or cEOS switch takes about 1.5 GB. Run one lab at a time: make stop the others first.

Get the cEOS image

Unlike SR Linux, cEOS-lab is not in a public registry. Download it once from arista.com (a free account is enough): EOS → 4.36 → EOS-4.36.3.2M → cEOS-lab. Take cEOSarm-lab-4.36.3.2M.tar.xz on Apple Silicon or cEOS64-lab-4.36.3.2M.tar.xz on Intel/AMD, and check it against its .sha512sum.

Downloads
$ xz -dc cEOSarm-lab-4.36.3.2M.tar.xz | docker import - ceos:4.36.3.2M
$ docker images ceos
REPOSITORY   TAG          SIZE
ceos         4.36.3.2M    3.89GB

example output The labs expect exactly the name ceos:4.36.3.2M.

The mixed 5-stage lab

The full 5-stage lab does not fit a laptop, so this one keeps one switch per position: one plane and two pods, each with one leaf and one spine, under one super-spine. Every role runs on Arista, and it has every kind of link: Arista to Nokia, Nokia to Arista and Arista to Arista. Traffic from pod 1 to pod 2 crosses all five stages.

Run it

The steps are those of the 3-stage lab, from the lab's own directory. The binary from step 2 is shared by all labs.

dorsi/test/fabric-5stage-mixed
$ cd test/fabric-5stage-mixed
$ WEBUI_PORT=3200 make start
DORSI Web UI: http://localhost:3200

Wait until every Arista switch answers that its NETCONF server is running (and give SR Linux its minute):

Terminal
$ for n in leaf1 spine2 superspine1; do
    docker exec dorsi-fabric-5stage-mixed-$n Cli -p 15 -c 'show management api netconf' | grep Server
  done
Server: running on port 830, in default VRF
... once per switch ...
dorsi/test/fabric-5stage-mixed
$ make copy
$ make run-and-configure

In the Web UI at http://localhost:3200 the topology shows the five switches with every fabric link up, BGP up and cabling ok, and no Problems.

What has and has not been verified. On this lab all four eBGP sessions come up, every switch learns the loopbacks of the other four, all 20 loopback pairs ping, and DORSI reports every fabric and server link up. There is one path between any two switches, so ECMP is not tested here (the 3-stage labs cover it), and a super-spine on SR Linux has only been checked by automated tests.

Stop and clean up

dorsi/test/fabric-3stage
$ make stop

This destroys all nine containers. For another lab, run make stop in its own directory. You can start again from step 3 at any time. If you used Colima, colima stop frees the memory.
